# support-agent

**客服 Agent 的最小可信实现：意图识别 → 工具调用 → 权限校验 → 人工兜底。**

标准库 Python，无第三方依赖，可离线演示。

```bash
python agent.py
python agent.py "我的订单 A1001 到哪了"
python agent.py "我要退款 A1002，咖啡机坏了"
```

## 为什么值得看

大多数「客服 Agent」示例把判断逻辑写进 if-chain，然后在演示里表现正常、在生产里越权。这个 demo 用四个刻意的设计点把「能演示」和「能上生产」分开：

| 设计点 | 做法 | 防的是什么 |
|---|---|---|
| **工具声明式注册** | 每个工具带参数 schema + 权限谓词，加到 `TOOLS` 字典即可 | if-chain 越长越难审计，加一个工具要改三处 |
| **权限在工具执行前** | `_own_order()` 先校验归属，再跑 `run()` | 模型自信地查了别人的订单 |
| **自治上限** | 退款 > ¥500 转人工，不需要模型判断 | 「模型觉得可以退」导致的资损 |
| **转人工是一等公民** | 意图未知 / 工具失败 / 超阈值，三种情况都走 handoff 并说明原因 | 把「不会」伪装成「已处理」 |

另外每次决策都留 `trace`（意图、命中关键词、工具、参数、结局、转人工原因），事后可审计。

## 实测

```
RESULT: 6/6 turns behaved as expected
```

覆盖的六种情形：

1. 闲聊 → 正常回复，不转人工
2. 查自己的订单 → 调 `check_order`，回状态与物流
3. 退款 ¥1299 → 超过 ¥500 上限，转人工（说明金额与原因）
4. 退款别人的订单 → 权限拒绝，转人工
5. 查别人的订单 → 权限拒绝，转人工
6. 无法识别意图 → 转人工

## 和真实系统的差距

诚实说明，避免被当成生产代码：

- **意图识别是规则匹配**，不是模型。真实系统会用小模型做分类，规则兜底。这里选规则是因为它可解释、可测试，而演示的重点在工具编排与权限。
- **订单服务是内存字典**。真实系统要走 gRPC/REST + 幂等键，退款必须有幂等 ID，否则重试会重复退款。
- **没有会话记忆**。多轮澄清（「就是刚才那个订单」）需要会话状态，这里每轮独立。
- **转人工没有实际通道**。真实系统要接工单系统或 IM，并保证转接过程不丢上下文。
